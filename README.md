# API Testing Agent

**ВКР:** «Разработка интеллектуальной агентной системы функционального тестирования REST API по спецификации OpenAPI с использованием локальных языковых моделей».

**Автор:** Прокофьев Илья Викторович, группа РТ5-81Б.

Проект посвящён приложению, которое по OpenAPI и сформулированной пользователем цели проверяет разрешённый тестовый REST API. Локальная языковая модель предлагает следующий шаг, а программа проверяет допустимость действия, выполняет HTTP-запрос, сопоставляет ответ с контрактом и сохраняет свидетельства. Агентный цикл нужен для сценариев, где последующие действия зависят от фактических ответов API.

Планируемый результат включает ограниченный профиль OpenAPI, безопасный доступ к одному разрешённому test target на Project, последовательный agent loop, детерминированную проверку ответов, историю запусков и находок, терминальный интерфейс Textual и сбрасываемый Demo API. Под «диагностикой» понимается анализ наблюдаемых HTTP- и контрактных отклонений, а не доказательство внутренней причины дефекта.

**Текущее состояние:** реализованы S01 (локальная MiniCPM5-2B Q4_K_M и вызовы инструментов) и S02 (первый реальный HTTP-сценарий). S02 выполняет `execute_operation(getPet) → GET /pets/1 → observation → finish_run` с проверяемым exchange ID. Полное приложение ещё не реализовано; следующий продуктовый срез — поддерживаемый профиль OpenAPI.

Для повторения S01 нужен локальный GGUF и Windows runtime из источников, указанных в lock-файле; бинарники не хранятся в Git. Запустите runtime командой из lock-файла, затем `python scripts/check_stage.py S01 good` и `python scripts/check_stage.py S01 bad`. Good должен завершиться с `0`, bad — с `2`. Сырые логи, trace и измерения лежат локально в `evidence/S01` и передаются ревьюеру отдельно. Остальные документы и отчёты по решению автора также хранятся локально и не публикуются в Git.

## Запуск первого HTTP-сценария

Проверено на Windows, Python 3.13.5; новый код использует стандартную библиотеку.
Из корня проекта запустите локальную модель командой из `experiments/local_model/runtime-lock.json`.
Дождитесь готовности `http://127.0.0.1:18081/health`, затем выполните:

```powershell
python -m unittest discover -s tests -p 'test_*.py' -q
python scripts/check_stage.py S02 good
python scripts/check_stage.py S02 bad
```

Good требует работающий runtime и локальный GGUF с закреплённым SHA-256. Gate сам
поднимает Demo API на свободном порту, сбрасывает его и проверяет ровно один GET
по независимому журналу сервера. Bad работает без модели: проверяет лишние аргументы,
чужой адрес/порт, redirect, источники OpenAPI, бюджет запроса и ссылки evidence.
Коды завершения: good `0`, ожидаемое отклонение bad `2`, ошибка gate `1`.
В PowerShell смотрите `$LASTEXITCODE` сразу после команды; в автоматизации передавайте
его вызывающему процессу через `exit $LASTEXITCODE`.

Результаты сохраняются в `evidence/S02/good.json`, `bad.json`, `trace.json` и отдельных
серверных журналах. Каталог можно изменить через `S02_EVIDENCE_DIR`; адрес runtime —
через `S02_LLM_BASE_URL`. Разрешён только числовой loopback HTTP с явным портом.
Файлы evidence игнорируются Git и передаются ревьюеру отдельно.

Отдельный Demo API можно запустить через `python -m demo_api.server --port 18082`;
после запуска он содержит `{"id":1,"name":"Murka"}` на `/pets/1`. Для испытаний
reset выполняет управляющий стенд через `DemoServer.reset()`, модель не получает это право.

Контур принимает только локальную fixture `tests/fixtures/demo_openapi.json`.
Общий парсер OpenAPI пока не реализован. HTTP идёт прямо на `127.0.0.1`, без DNS,
proxy, redirect и повторов; на Run разрешён один запрос, ответ ограничен 64 КиБ,
тайм-аут HTTP — 5 секунд, бюджет Run — 180 секунд, два хода LLM — до 90 секунд каждый.
Инфраструктурный сбой сохраняется отдельно и не создаёт Finding об API.

После первого HTTP-среза требуется независимое ревью и повторные испытания
в новой чистой сессии. Машинные gate не заменяют такое ревью.

## Правила сопровождения кода

Подробные комментарии и docstring пишутся на русском языке. Объясняйте назначение
компонентов, границы доверия, ограничения и причины нетривиальных решений.
Новые файлы называются по смыслу, без номера этапа; номера используются для gate
и evidence. В коммиты входят только относящиеся к системе исходники, тесты,
фикстуры и инструкции запуска. Локальные документы, отчёты, веса и evidence
остаются вне Git; для новой сессии передавайте актуальный AGENTS.md отдельно.
